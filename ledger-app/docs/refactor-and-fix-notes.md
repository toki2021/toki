# 自动记账 App · 代码重构与问题修复说明

> 说明：本文档总结对 `AutoLedger`（自动记账 Android App）做的一轮代码审查与集中修复。
> 修复目的不是"加新功能"，而是清理历史遗留的质量问题——精度、稳定性、隐私合规、性能、可维护性等。
> 所有改动均可在 Git 提交历史中回滚。

---

## 一、问题归类概览

| 类别 | 说明 | 对 App 的影响 |
| --- | --- | --- |
| 安全与合规 | 隐私泄露、权限敏感、黑名单写死 | 隐私更可靠，利于应用商店上架 |
| 正确性与稳定性 | 金额精度、协程泄漏、删除不可撤 | 账更准、运行更稳、误删可救 |
| 性能 | 界面重绘、动画开销、DB 查询 | 更流畅、低配机也能跑顺 |
| 体验与工程质量 | 全局状态、颜色、国际化、可访问性 | 统一、好维护、更友好 |

## 二、安全与合规类

### 1. 敏感日志（日志守卫）
- **问题**：release 包中把已解析的**商户名、金额**写入系统日志，可能泄露用户账目信息。
- **修改**：为所有日志增加 `BuildConfig.DEBUG` 条件守卫，仅调试版输出。
- **影响**：普通用户无感知；避免隐私投诉与审核风险。

### 2. 商户"黑名单"外置
- **问题**：判断"通用商户名（如『交易』『转账』）"的逻辑此前硬编码在多处，改动需改多处并重新发版。
- **修改**：抽离为独立配置（`merchant_filters.json`），集中管理，并支持远程更新。
- **影响**：识别规则可独立调整，降低维护成本，提升识别准确率。

### 3. 隐私声明
- **问题**：App 使用通知监听、读屏/截屏等敏感权限，未向用户正式说明。
- **修改**：在设置页新增完整隐私说明，明确数据仅本机处理、即用即删、不上传。
- **影响**：满足应用商店对敏感权限的合规要求，符合"隐私优先"产品定位。

## 三、正确性与稳定性类

### 4. 金额精度（本次最关键修复之一）
- **问题**：原代码用 `Math.round(yuan * 100)` 换算，存在浮点误差（如 `123.45 → 12344/12345`），对账目类 App 是硬伤。
- **修改**：统一改用 `BigDecimal`（`movePointRight(2).longValueExact()`）精确换算分。
- **影响**：每一笔账金额精确，杜绝"记的与花的对不上"。

### 5. 协程 / 资源泄漏
- **问题**：通知监听、无障碍读屏等后台服务退出时未取消协程作用域，长期运行会卡顿、耗电甚至崩溃；广播接收无超时保护。
- **修改**：`onDestroy` 统一取消作用域；广播处理增加 `goAsync()` + `withTimeoutOrNull(8s)` 兜底。
- **影响**：后台稳定性与省电提升。

### 6. 全局可变状态
- **问题**：界面风格这类状态原为全局 `object` + `mutableStateOf`，多页面共享易错乱。
- **修改**：迁移为规范的 `ViewModel + StateFlow`（`UiVariantViewModel`）。
- **影响**：状态管理更可控；本项后续（见下文"界面不同步修复"）排查出的真实 bug 也源于此。

### 7. 删除可撤销
- **问题**：原删除为静默删除，误删无法找回。
- **修改**：删除改走 Repository + 弹出 Snackbar「撤销」，短时间内可恢复。
- **影响**：误删有救，用户体验更友好。

## 四、性能类

### 8. 重组热点与动画性能
- **问题**：首页/统计页在数据变化时整块重算；金额滚动动画每帧用 `String.format` 重新解析。
- **修改**：用 `remember` / `derivedStateOf` 缓存重复计算；复用预创建的 `DecimalFormat`。
- **影响**：滚动与数字动画更丝滑，减少卡顿。

### 9. 数据库查询优化
- **问题**：为展示"最近使用的商户 / 待处理计数"，原实现会拉取整表再内存过滤，数据量大时变慢。
- **修改**：新增专用 DAO 查询（`observeRecentMerchants(n)`、`observeCount()`），在 SQL 层完成过滤。
- **影响**：账目增多后页面与联想仍保持流畅。

## 五、体验与工程质量类

### 10. 界面风格切换不同步（本次新发现并修复）
- **问题**：经实测发现，设置页 / 首页各自通过 `viewModel()` 拿到了**独立的** `UiVariantViewModel` 实例，导致"设置里切换界面风格无反应、首页大卡片不联动"。
- **修改**：统一改为在导航层持有**单个 Activity 级实例**，通过参数注入到首页与设置页（主题、底栏、首页、设置全部同步）。
- **影响**：界面风格切换现在**实时全局生效**，且重启后记住选择。已用真机日志验证。

### 11. 导航参数类型安全
- **问题**：导航路由参数此前手工解析，存在类型隐患。
- **修改**：用 `navArgument(NavType.LongType)` 定义参数类型，并处理 `onNewIntent` 深链。
- **影响**：导航更健壮。

### 12. 颜色 Token 化
- **问题**：大量颜色硬编码在各 Composable 中，改主题需逐处修改。
- **修改**：统一抽取到 `Theme` 色彩 Token。
- **影响**：视觉统一，主题维护更方便。

### 13. 字符串国际化 + 可访问性
- **问题**：界面文案大多硬编码；图标/按钮缺无障碍描述。
- **修改**：全部文案收拢到 `strings.xml`（为未来多语言铺路）；为删除按钮、预览条等添加 `contentDescription`。
- **影响**：可国际化、对读屏用户友好、结构更整洁。

### 14. SDK 范围统一（清理废弃 API）
- **问题**：使用了新版 API 标记废弃的写法（如 `Icons.Filled.List`、无参 `menuAnchor()` 等）。
- **修改**：替换为推荐写法（`AutoMirrored` 图标、带 `MenuAnchorType` 的锚点等）。
- **影响**：编译零警告，为后续升级 SDK 扫清障碍。

## 七、金额识别专项修复（第三轮，用户实测"付14.60优惠0.46"场景）

### 问题一：优惠金额被记成入账金额
- **现象**：支付 14.60、优惠 0.46（实付 14.14）时，记账 App 入账了 0.46。
- **根因**：支付结果页上大字号实付金额常被 OCR 拆成 `"¥"` + `"14.14"` 两行，两行都匹配不到金额规则；页面上唯一完整的 ¥ 金额只剩小字号的"已优惠¥0.46"，被当成了实付。
- **修复**（`BillPageParser`）：
  1. `joinSplitYuan`：把拆开的 `"¥"` + `"14.14"` 拼回一行（含"已支付¥"+数字形态）；
  2. 优惠语境剔除：行内含"已优惠/立减/满减/折扣/抵扣"的金额不算实付；优惠词单独成行时，紧随其后的金额也不算；
  3. 期望金额锚定：通知侧解析出的实付金额为权威值，OCR 页面只需确认存在即采用——**OCR 只负责补商户，绝不改写金额**（`BillReaderService` 透传 `expectedAmountCents`）；
  4. 强页面判定：只有"支付成功/微信支付凭证/付款详情"等结果页特征才允许 OCR 凭空新建待确认，"恭喜获得¥红包"类营销弹窗一律拦截。
- **同修**：无障碍树路径（原生页）的金额挑选从"取第一个 ¥"改为同一套"实付标签 → 优惠剔除 → 唯一主金额"规则。

### 问题二：带优惠的真实账单被整条误杀（上一轮引入的回归）
- **现象**："支付成功，已优惠0.46，实付14.14元"这类正常账单通知不再被记录。
- **根因**：上一轮的营销噪音词表含"优惠/积分/红包"等词，会把带这些字样的真实支付通知一并拒绝；支付宝标准通知"你有一笔X元的支出，点击领取10个支付宝积分"也被"积分"误杀。
- **修复**（`PaymentParser.looksLikePayment`）：废弃词表硬拒，改为纯支付信号门——只认"支付成功/已支付/转账成功/退款成功"等明确信号、"向XX转账"句式、支付宝"你有一笔X元的支出"实付句式。营销通知（红包失效/多笔立减/订单送达）天然不含这些信号，仍被拦截。
- **金额解析**：优先"实付/支付金额/合计"标签金额；剔除优惠语境后主金额须唯一，多个宁可不猜（进待处理手动补）。

### 诊断日志
- DEBUG 包新增 `PayNotify`（通知原文）、`BillReader`（OCR 行 / 解析出的金额与商户 / handleBill 各分支决策）日志；release 一律不打，符合隐私约定。
- 单元测试补充优惠场景与通知过滤门用例（共 40 个用例全部通过）。
